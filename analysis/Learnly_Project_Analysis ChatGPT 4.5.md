# Обзор проекта Learnly

**Learnly** – это интерактивный обучающий проект на основе Jupyter Notebook, предназначенный для обучения программированию (на примере Python) с помощью пошаговых уроков. Проект сочетает теоретические объяснения, примеры кода и практические задания, позволяя ученику писать код прямо в ноутбуке и получать мгновенную обратную связь. Архитектура приложения разделена на несколько модулей: основной движок обучения (`LearnlyEngine` в файле `engine.py`), генерация уроков и заданий с помощью ИИ (`lesson.py`), отображение контента в ноутбуке (`display.py`), а также интерактивный ноутбук-пример использования (`learnly.ipynb`). Ниже представлен подробный анализ каждого компонента, выявлены проблемы в реализации и предложены улучшения.

## Цель и функциональность проекта

**Цель проекта** – предоставить платформу для интерактивного обучения, где ученик последовательно проходит урок, состоящий из нескольких частей (теория, примеры, задания), и может получить подсказки или примеры кода, а также проверить свои решения. Основные функциональные возможности Learnly включают:
- **Последовательность урока:** Урок разделён на части (*LessonPart*): текстовые объяснения, блоки кода и практические задания. Ученик поэтапно изучает материал и выполняет задачи.
- **Интерактивность:** После каждой части урока ученик может нажать кнопку «Дальше» для перехода к следующей части. Для заданий предоставляются поля ввода для ответа, а также кнопки «Подробнее» (подсказка) и «Пример» (образец решения), что делает обучение гибким.
- **Автоматическая проверка решений:** Для практических заданий предусмотрена проверка решения – код ученика анализируется автоматически, и выводится сообщение об успехе или ошибке. Предусмотрены команды `hint`/`help` для запроса подсказки, `skip` – пропустить задание, и `finish` – досрочно закончить урок.
- **Память и прогресс:** Система ведёт журнал прогресса урока (`lesson_progress`) и сохраняет его в файл JSON, чтобы потенциально можно было восстановить состояние урока. В будущем планируется более продвинутая “память” – сохранение программы обучения, прогресса (выполненные задания, частые ошибки), данных об ученике и т.д. ([README.md](file://file-JfqCXbnsBKUdsYMM1Bxu49#:~:text=TODO%3A%20%D0%B2%20%D0%B1%D1%83%D0%B4%D1%83%D1%89%D0%B5%D0%BC%20,%D0%BE%D0%B1%20%D1%83%D1%87%D0%B5%D0%BD%D0%B8%D0%BA%D0%B5%3A%20%D1%83%D1%80%D0%BE%D0%B2%D0%B5%D0%BD%D1%8C%2C%20%D1%81%D1%82%D0%B8%D0%BB%D1%8C%20%D0%BE%D0%B1%D1%89%D0%B5%D0%BD%D0%B8%D1%8F)) ([README.md](file://file-JfqCXbnsBKUdsYMM1Bxu49#:~:text=,%D0%BE%D0%B1%D1%89%D0%B0%D1%82%D1%8C%D1%81%D1%8F%20%D1%81%20%D0%BF%D0%B0%D0%BC%D1%8F%D1%82%D1%8C%D1%8E)). Обсуждается хранение состояния как локально (файл, ноутбук), так и в облаке (например, Google Drive) ([README.md](file://file-JfqCXbnsBKUdsYMM1Bxu49#:~:text=%D0%92%D1%8B%D0%B1%D0%B8%D1%80%D0%B0%D0%B5%D0%BC%20%D0%BC%D0%B5%D1%81%D1%82%D0%BE%20%D1%85%D1%80%D0%B0%D0%BD%D0%B5%D0%BD%D0%B8%D1%8F)).

**Общая архитектура:** Проект написан на Python с использованием IPython/Jupyter Notebook. Он состоит из:
- Классов для представления частей урока и самого урока (модуль `engine.py`).
- Классов и функций для управления ходом урока (основной класс LearnlyEngine в `engine.py`).
- Модуля `display.py` для форматированного вывода контента (Markdown) и управления элементами интерфейса (ipywidgets).
- Модуля `lesson.py` для генерации новых частей урока, в том числе с использованием OpenAI API для автогенерации содержания.
- Jupyter Notebook (`learnly.ipynb`), демонстрирующего работу системы (вывод приветственного сообщения, отображение частей урока, интерактивные виджеты и пр.).

Далее рассмотрим подробно каждый модуль и его реализацию.

# Разбор модулей проекта

## Модуль `engine.py` (движок урока)

**Назначение:** Этот модуль содержит основные классы и логику управления учебным процессом. Здесь определены типы частей урока, класс урока и главный класс **LearnlyEngine**, отвечающий за последовательность урока, переходы между шагами, проверку решений и сохранение прогресса.

### Классы LessonPart и его потомки (TextPart, CodePart, AssignmentPart)

- **LessonPart** – абстрактный базовый класс, представляющий одну часть урока. Он хранит общие поля: `content` (содержимое части, например текст или условие задачи), `hint` (подсказка) и `example` (пример решения или код). При инициализации также фиксируется метка времени `timestamp` (время создания части) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=%D0%91%D0%B0%D0%B7%D0%BE%D0%B2%D1%8B%D0%B9%20%D0%BA%D0%BB%D0%B0%D1%81%D1%81%20%D0%B4%D0%BB%D1%8F%20%D1%87%D0%B0%D1%81%D1%82%D0%B5%D0%B9%20%D1%83%D1%80%D0%BE%D0%BA%D0%B0,time)). У класса есть абстрактный метод `display()`, который должен быть реализован в подклассах для отображения соответствующего контента, и методы сериализации:
  - `to_dict()` – преобразует объект части урока в словарь (для сохранения) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20to_dict%28self%29%20,self.timestamp)). В базовой реализации сохраняет `content`, `hint`, `example` и `timestamp`.
  - `from_dict(cls, data)` – класс-метод для восстановления объекта части урока из словаря ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=%40classmethod%20def%20from_dict%28cls%2C%20data%3A%20Dict,time.time%28%29%29%20return%20instance)). Он создает экземпляр `cls` (т.е. фактического подкласса) с использованием полей словаря. Обратите внимание: базовая реализация `from_dict` не знает про дополнительные поля подклассов, поэтому она подходит для TextPart и CodePart, но в случае AssignmentPart восстанавливает только базовые поля (см. замечание об ошибках ниже).

- **TextPart** – подкласс LessonPart для текстовой теории. Реализует метод `display(self, display_instance, part_index)`, который вызывает `display_instance.show_text_content(self.content, part_index)` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20display,display_instance.show_text_content%28self.content%2C%20part_index)). То есть, для текстовой части выводится оформленный Markdown с содержанием. В `to_dict()` этот класс дополняет словарь типом части: `data["type"] = "text"` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20to_dict%28self%29%20,return%20data)).

- **CodePart** – подкласс для блоков кода (примеров). Он аналогичен TextPart в текущей реализации: `display()` вызывает `show_text_content` (возможно, планировалось особое форматирование кода, например, в виде блока `code` Markdown) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20display,display_instance.show_text_content%28self.content%2C%20part_index)). В `to_dict()` добавляет `"type": "code"` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20to_dict%28self%29%20,return%20data)).

- **AssignmentPart** – подкласс для практического задания. Кроме унаследованных полей, в конструкторе добавлены поля `success_message` (сообщение при успешном выполнении, по умолчанию `"Отлично! Задание выполнено верно."`) и `error_message` (сообщение при ошибке, по умолчанию `"Проверьте ваше решение и попробуйте снова."`) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20__init__,error_message%20%3D%20error_message)). Метод `display()` показывает условие задания через `display_instance.show_assignment(self.content, part_index)` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20display,display_instance.show_assignment%28self.content%2C%20part_index)). Метод `to_dict()` добавляет к словарю тип `"assignment"` и поля `success_message` и `error_message` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20to_dict%28self%29%20,%3D%20self.error_message%20return%20data)) для сохранения полного состояния задания. Таким образом, AssignmentPart хранит не только условие и подсказку, но и тексты ответов для обратной связи.

### Класс Lesson (урок)

**Lesson** представляет целый урок, содержащий заголовок и список частей (экземпляров LessonPart). В конструкторе задаётся `title` урока и необязательный список частей `parts` (если не указан, инициализируется пустым списком) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20__init__,parts%20%3D%20parts%20or)). Основные методы:
- `add_part(part)` – добавить новую часть (объект TextPart/CodePart/AssignmentPart) в урок (добавляется в список `parts`) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.parts%20%3D%20parts%20or%20)).
- `to_dict()` – сохранить весь урок в словарь, содержащий заголовок и список частей (каждая часть через свой `to_dict()`) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20to_dict%28self%29%20,)). Результат – словарь вида `{"title": ..., "parts": [ {...}, {...}, ...]}`.
- `from_dict(cls, data)` – восстановить урок из словаря ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=%40classmethod%20def%20from_dict%28cls%2C%20data%3A%20Dict,part%20%3D%20AssignmentPart.from_dict%28part_data)). Создаётся экземпляр Lesson с заголовком (или `"Без названия"`, если не указан). Затем для каждой части из списка `data["parts"]` проверяется поле `"type"` и в зависимости от него создаётся соответствующий объект части урока:
  - Если `type == "text"`, используется `TextPart.from_dict(...)`.
  - Если `type == "assignment"`, вызывается `AssignmentPart.from_dict(...)`.
  - Иначе (например, `"code"` или любой другой тип) – эта часть пропускается (`continue`) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=for%20part_data%20in%20data.get%28,add_part%28part)). Здесь заметен недочёт: тип `"code"` не обрабатывается, и такой элемент просто игнорируется при загрузке ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=for%20part_data%20in%20data.get%28,add_part%28part)). Это означает, что сохранённые части с кодом не восстановятся из JSON (см. раздел об ошибках). Аналогично, для заданий AssignmentPart применяется базовый `from_dict`, не восстанавливающий `success_message` и `error_message`, т.к. спецобработки для них нет.

### Класс LearnlyEngine (основной движок обучения)

**LearnlyEngine** – центральный класс, управляющий ходом урока. Его задачи: инициализация урока, отображение частей, реагирование на действия пользователя (нажатия кнопок, ввод кода), проверка решений, переход к следующим заданиям и сохранение прогресса.

Основные поля и инициализация:
- При создании `LearnlyEngine.__init__` загружает начальный урок через `create_new_lesson()` из модуля `lesson.py` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20__init__%28self%29%3A%20self,tasks%27%3A)). Судя по коду, `create_new_lesson` возвращает словарь с базовыми частями урока (приветствие и простой пример кода) – по сути шаблон урока ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=def%20create_new_lesson%28%29%3A%20return%20%7B%20,print%28%27Hello%2C%20world)). Однако далее в процессе работы движок заменяет этот урок на новый (в методе `begin_lesson`), поэтому начальный урок из `create_new_lesson` может служить заглушкой или не использоваться. Также в `__init__` создаётся объект отображения `LearnlyDisplay()` для вывода на экран ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20__init__%28self%29%3A%20self,str%2C%20Any%5D%5D%20%3D)).
- `lesson_progress` – список для сохранения прогресса прохождения урока (каждый шаг или действие записывается как словарь с информацией о части, времени и т.п.). Файл для хранения прогресса задан как `lesson_file = "lesson.json"` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.display%20%3D%20LearnlyDisplay%28%29%20self.lesson_progress%3A%20List,tasks%27%3A)).
- `current_part_index` – индекс текущей части урока (начинается с 1) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.display%20%3D%20LearnlyDisplay%28%29%20self.lesson_progress%3A%20List,tasks%27%3A)). **Замечание:** индекс 1 установлен сразу, что может быть неинтуитивно (обычно ожидался бы 0 перед началом). Однако в `begin_lesson` индекс потом сбрасывается на 0 ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self)).
- `memory` – словарь для хранения данных, связанных с динамическими заданиями. Инициализируется как `{'tasks': {}}` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.lesson_file%20%3D%20,tasks%27%3A)). Здесь будут сохраняться сгенерированные задания (непредусмотренные изначально уроком, а добавленные на лету).

После инициализации движок сразу же вызывает `_save_progress()`, создавая или очищая файл `lesson.json` с текущим прогрессом (пока пустой список) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.memory%3A%20Dict%5Bstr%2C%20Any%5D%20%3D%20,)).

Основные методы LearnlyEngine:
- **Начало и ход урока:** 
  - `start_lesson()` – старт учебной сессии. Выводит приветственное сообщение (`display.show_welcome_message()`), затем пытается загрузить сохранённый прогресс из файла `lesson.json` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self)). Если файл существует и содержит корректные данные, прогресс загружается в `self.lesson_progress`; иначе прогресс остаётся пустым (обработка исключений FileNotFoundError, JSONDecodeError) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=try%3A%20with%20open%28self.lesson_file%2C%20%22r%22%2C%20encoding%3D%22utf,lesson_progress%20%3D)). Далее отображается ранее пройденный прогресс (если был) через `display.show_lesson_progress()` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=)) – это позволяет напомнить ученику, на чём он остановился, показав пройденные части и ответы. После этого вызывается `self.begin_lesson()`, запускающий сам урок.
  - `begin_lesson()` – инициализирует структуру урока. В текущей реализации он **заменяет** текущий урок на новый, созданный прямо в коде. Например, задаётся урок с заголовком `"Введение в Python"` и тремя частями: 
    1. TextPart с приветствием и кратким описанием Python (с подсказкой и примером кода) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,)).
    2. AssignmentPart с заданием “Напишите функцию, которая принимает два числа и возвращает их сумму.” (с подсказкой и примером реализации функции) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=%29%2C%20AssignmentPart%28%20content%3D,%D0%9F%D1%80%D0%BE%D0%B4%D0%BE%D0%BB%D0%B6%D0%B8%D0%BC)).
    3. TextPart с сообщением об успешном выполнении задания и переходе к более сложным темам ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=TextPart%28%20content%3D,example)).
    
    Эти части добавляются в объект урока `Lesson` через `lesson.add_part` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=)). После формирования урока, индекс текущей части сбрасывается на 0 и вызывается `_display_current_part()` для отображения первой части ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self)).
  - `_display_current_part()` – внутренний метод, отвечающий за вывод на экран текущей части урока. Он получает текущий объект части по индексу и вызывает его метод `display()` для отображения контента ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=current_part%20%3D%20self.lesson.parts)). Класс `LearnlyDisplay` формирует соответствующий Markdown (см. `display.py`). 
    - Если текущая часть – это задание (AssignmentPart), движок дополнительно создаёт виджет **Textarea** для ввода ответа учеником ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,description_width%27%3A%20%27initial%27%7D%20%29%20display%28answer_widget)). Поле помечено как “Ваш ответ” и предназначено для ввода кода решения.
    - После отображения контента (и поля ввода, если есть) метод записывает событие в `lesson_progress`: добавляется запись со ссылкой на тип части (text/assignment), содержимое, номер части и временную метку ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,current_part.__class__.__name__.lower%28%29.replace%28%27part%27%2C)). Запись прогресса сразу сохраняется на диск через `_save_progress()` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self)).
    - Затем создаются кнопки управления (следующая часть, подсказка, пример, завершение) с помощью `_create_command_widget()` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,handle_button_click%28b%2C%20part%29%29%20display%28command_buttons)). Эти кнопки отображаются под частью урока, и для каждой кнопки устанавливается обработчик нажатия – лямбда, вызывающая `_handle_button_click` с передачей нажатой кнопки и текущей части урока ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=command_buttons%20%3D%20self,handle_button_click%28b%2C%20part%29%29%20display%28command_buttons)). Таким образом, любые клики пользователя по кнопкам будут обработаны методом `_handle_button_click` с контекстом текущей части.
    
  - `_create_command_widget()` – вспомогательный метод, который формирует горизонтальный блок (`widgets.HBox`) из четырёх кнопок: **«Дальше»**, **«Подробнее»** (подсказка), **«Пример»**, **«Закончить урок»】. Каждой кнопке задаётся описание (label), иконка и стили (цвет фона, текста и др.) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20_create_command_widget%28self%29%20,%D0%BE%D1%87%D0%B5%D0%BD%D1%8C%20%D1%82%D0%B5%D0%BC%D0%BD%D1%8B%D0%B9%20%D1%81%D0%B8%D0%BD%D0%B8%D0%B9%20%27font_weight%27%3A%20%27normal)) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=details_button%20%3D%20widgets,)) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=example_button%20%3D%20widgets,)) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=finish_button%20%3D%20widgets,%D1%82%D0%B5%D0%BC%D0%BD%D1%8B%D0%B9%20%D1%81%D0%B5%D1%80%D1%8B%D0%B9%20%27font_weight%27%3A%20%27normal%27)). Кнопки упаковываются с отступами между ними ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,Layout%28%20gap%3D%2710px%27%2C%20padding%3D%275px%27%20%29)). Этот интерфейс позволяет пользователю управлять ходом урока.
  
  - `_handle_button_click(button, part)` – обрабатывает нажатие кнопок управления уроком ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20_handle_button_click%28self%2C%20button%3A%20widgets,finish_lesson)) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.display.show_hint%28part.hint%29%20self.lesson_progress.append%28%7B%20,description%20%3D%3D%20%27%D0%9F%D1%80%D0%B8%D0%BC%D0%B5%D1%80)) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.display.show_example%28part.example%29%20self.lesson_progress.append%28%7B%20,description%20%3D%3D%20%27%D0%97%D0%B0%D0%BA%D0%BE%D0%BD%D1%87%D0%B8%D1%82%D1%8C%20%D1%83%D1%80%D0%BE%D0%BA)). Логика зависит от текста кнопки:
    - **«Дальше»:** увеличить `current_part_index` на 1 (переходим к следующей части). Если новая часть существует (индекс меньше длины урока), вызывается `_display_current_part()` для её отображения. Если частей больше нет – вызывается `finish_lesson()` для завершения урока ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,description%20%3D%3D%20%27%D0%9F%D0%BE%D0%B4%D1%80%D0%BE%D0%B1%D0%BD%D0%B5%D0%B5)).
    - **«Подробнее» (подсказка):** выводит подсказку для текущей части (`display.show_hint(part.hint)`) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=elif%20button,part.hint)). Также добавляет в прогресс запись о том, что была запрошена дополнительная информация (действие `"расскажи подробнее"`, сохраняется содержимое подсказки и время) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.display.show_hint%28part.hint%29%20self.lesson_progress.append%28%7B%20,time.time%28%29%20%7D%29%20self._save_progress)). Прогресс сохраняется в файл.
    - **«Пример»:** аналогично, выводит пример решения `display.show_example(part.example)` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=elif%20button,time.time)) и логгирует действие `"приведи пример кода"` с сохранением примера в прогресс ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.display.show_example%28part.example%29%20self.lesson_progress.append%28%7B%20,time.time%28%29%20%7D%29%20self._save_progress)).
    - **«Закончить урок»:** немедленно завершает урок вызовом `finish_lesson()` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self,finish_lesson)).
    
    > **Примечание:** Кнопки «Подробнее» и «Пример» актуальны, только если для части урока заданы непустые поля `hint` или `example`. В текущем контенте урока (см. `begin_lesson`) эти поля заданы для первой текстовой части и для задания. Если подсказка или пример отсутствуют, функция `display.show_hint/example` всё равно вызовется, но, вероятно, просто выведет пустое содержимое.
  
- **Управление заданиями и проверка решений:**
  - `get_next_task()` – (вспомогательный) генерирует следующее задание для практики. В текущей реализации эта функция **заглушка**: она возвращает фиксированный словарь с шаблонным условием задачи (текст “Задание N: Напишите функцию для...”), подсказкой, сообщениями успеха/ошибки, а также ключевым элементом `'check': lambda ns: ...` – лямбда-функцией для проверки решения ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20get_next_task%28self%29%20,solution)). В данном примере `check` проверяет, что в пространстве имён `ns` определена функция `solution` (т.е. пользователь должен написать функцию с именем `solution`). Функция `get_next_task` добавляет сгенерированное задание в `self.memory['tasks']` под новым индексом (ключ – текущий размер словаря, т.е. порядковый номер задания начиная с 0) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=%27check%27%3A%20lambda%20ns%3A%20%27solution%27%20in,task_index%5D%20%3D%20task%20return%20task)). Затем возвращает созданный словарь задачи. В реальной ситуации вместо статичного примера должно происходить обращение к ИИ или другому источнику задач (см. `lesson.py`), однако пока логика упрощена.
  
  - `show_task(task_index)` – запускает показ задания с указанным номером. Если задание с таким индексом отсутствует в `memory['tasks']`, сначала пытается сгенерировать новое через `get_next_task()` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20show_task%28self%2C%20task_index%3A%20int%29%20,return)). Если генерация не удалась (функция вернула None), выводит сообщение об ошибке и прекращает ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=if%20task_index%20not%20in%20self.memory,return)). Иначе – получает задачу из `memory` и отображает её: выводит условие задания (`display.show_assignment(...)`) и сразу создаёт ячейку для ввода решения `create_solution_cell(...)` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.display.show_assignment%28%20self.memory)). Метод `create_solution_cell(problem)` формирует в ноутбуке новую кодовую ячейку с магической командой `%%check_solution` и текстом условия задачи в виде комментария ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20create_solution_cell%28self%2C%20problem%3A%20str%29%20,replace%3DFalse)). Эта ячейка появляется под текущей, предлагая ученику написать код решения прямо там (после строки `# Напишите ваше решение здесь:`). Параллельно `show_task` добавляет запись в прогресс о показанном задании (тип `"assignment"`, контент задачи и время) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,time.time%28%29%20%7D%29%20self._save_progress)) и сохраняет прогресс.
  
  - `create_solution_cell(problem)` – (см. выше) использует IPython API: `get_ipython().set_next_input(...)` для программного создания следующей ячейки. Она помечается магической командой `%%check_solution` и включает переданное условие задачи, отформатированное методом `_wrap_text` в виде комментариев, чтобы условие было видно внутри новой ячейки ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20create_solution_cell%28self%2C%20problem%3A%20str%29%20,replace%3DFalse)). В итоге ученик видит новую ячейку, начинающуюся с `%%check_solution` и содержащую текст задачи как комментарий. Предполагается, что ученик напишет свой код решения под этими комментариями.
  
  - `_wrap_text(text, max_length=77)` – утилита для форматирования длинного текста задачи в виде комментариев, не превышающих указанную длину строки. Она разбивает текст на слова и формирует строки, каждая начинается с `# ` (то есть в коде будет воспринята как комментарий) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=words%20%3D%20text,)). Это нужно, чтобы условие задачи в ячейке решения отображалось удобно читаемым комментарием.
  
  - `check_solution(cell: str, user_namespace: dict)` – **ключевой метод проверки решения**, который должен вызываться при выполнении учеником ячейки `%%check_solution`. Он принимает содержимое ячейки (строку с кодом решения, введённым учеником) и `user_namespace` – словарь переменных, образовавшийся после выполнения кода (т.е. пространство имён, где могут появиться решения студента). Логика проверки:
    - Сначала очищается и переводится в нижний регистр текст ячейки (`clean_cell`) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=clean_cell%20%3D%20cell)). Если в тексте присутствует ключевое слово `hint` или `help` (без учёта регистра), то вызывается `show_hint(self.current_part_index)` – показать подсказку для текущего задания ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=if%20any,hint%27%2C%20%27help%27%5D%29%3A%20self.show_hint%28self.current_part_index%29%20return)), и проверка на этом заканчивается. Таким образом, ученик может в ячейке с решением написать слово "hint", чтобы запросить подсказку (вместо решения).
    - Если в тексте найдено слово `finish`, вызывается `finish_lesson()` – принудительное завершение урока ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=if%20%27finish%27%20in%20clean_cell%3A%20self,return)). Если найдено слово `skip`, вызывается `skip_task()` – пропуск текущего задания ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=if%20%27skip%27%20in%20clean_cell%3A%20self,return)).
    - Если ни специальные команды, ни подсказка не обнаружены, происходит собственно проверка: берётся индекс задания `task_index = self.current_part_index` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=task_index%20%3D%20self,task_index)). Предполагается, что для текущего задания в `self.memory['tasks']` есть запись с таким ключом. Если она есть, вытаскивается словарь `task`. Далее внутри блока `try` вызывается функция проверки `task['check'](user_namespace)` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=task%20%3D%20self.memory,problem)). Напомним, `check` – лямбда, определённая при генерации задания, которая анализирует пространство имён. Если `check` возвращает True (решение правильное):
      - Выводится сообщение успеха `display.show_success(task['success'])` (например, “Отлично! Задание выполнено правильно.”) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=task%20%3D%20self.memory,problem)).
      - Делается небольшая пауза `time.sleep(1)` (вероятно, чтобы ученик успел увидеть сообщение) и вызывается `advance_to_next_task()` – переход к следующему заданию (см. ниже) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=task%20%3D%20self.memory,problem)).
    - Если `check` возвращает False (решение неправильное):
      - Выводится сообщение об ошибке `display.show_error(task['error'])` (“В вашем решении есть ошибка. Попробуйте еще раз.”) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=task%20%3D%20self.memory,problem)).
      - Снова создаётся ячейка решения с тем же условием `create_solution_cell(task['problem'])`, чтобы ученик попробовал ещё раз ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=else%3A%20self.display.show_error%28task,self.create_solution_cell%28task%5B%27problem)).
    - В случае, если при проверке кода возникает исключение (например, ошибка исполнения пользовательского кода), оно ловится и выводится через `display.show_error(f"Ошибка при проверке: {e}")` ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.create_solution_cell%28task,self.create_solution_cell%28task%5B%27problem)), и также генерируется новая ячейка для попытки решения ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.create_solution_cell%28task,self.create_solution_cell%28task%5B%27problem)).
    - Если почему-либо задания с текущим индексом нет в `memory['tasks']` (что не должно случиться при корректном использовании `show_task`), метод просто завершится без действий – явной обработки этой ситуации нет (можно было бы вывести сообщение об ошибке, как сделано в `show_hint`) .

  - `advance_to_next_task()` – увеличивает `current_part_index` на 1 и сразу вызывает `show_task` для нового значения индекса ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20advance_to_next_task%28self%29%20,self.current_part_index%20%2B%3D%201%20self.show_task%28self.current_part_index)). Таким образом, запускается следующее задание (динамически созданное). Эта функция используется, когда предыдущее задание решено правильно, чтобы автоматически выдать следующую задачу.

  - `skip_task()` – пропускает текущее задание. Добавляет запись в прогресс (действие `"пропуск_задания"`, указывает индекс задания и время) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20skip_task%28self%29%20,time.time%28%29%20%7D%29%20self._save_progress)), сохраняет прогресс и затем вызывает `advance_to_next_task()` для перехода к следующему заданию ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,save_progress)). Предусмотрен как реакция на команду `skip` внутри ячейки решения.

  - `show_hint(task_index)` – показывает подсказку для задания с данным индексом. Если в `memory['tasks']` есть такое задание, выводит подсказку `display.show_hint(...)` и вновь создаёт ячейку решения для повторной попытки ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20show_hint%28self%2C%20task_index%3A%20int%29%20,hint)). Также логирует это действие в прогресс (действие `"запрос_подсказки"`) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,%D0%9D%D0%B5%20%D1%83%D0%B4%D0%B0%D0%BB%D0%BE%D1%81%D1%8C%20%D0%BD%D0%B0%D0%B9%D1%82%D0%B8%20%D1%82%D0%B5%D0%BA%D1%83%D1%89%D0%B5%D0%B5%20%D0%B7%D0%B0%D0%B4%D0%B0%D0%BD%D0%B8%D0%B5)) и сохраняет прогресс. Если задания с таким индексом нет, выводит сообщение об ошибке (“Не удалось найти текущее задание”) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=%7D%29%20self._save_progress%28%29%20else%3A%20self.display.show_error%28,%D0%BD%D0%B0%D0%B9%D1%82%D0%B8%20%D1%82%D0%B5%D0%BA%D1%83%D1%89%D0%B5%D0%B5%20%D0%B7%D0%B0%D0%B4%D0%B0%D0%BD%D0%B8%D0%B5)).

- **Завершение урока и сохранение:**
  - `finish_lesson()` – завершает урок. Добавляет в `lesson_progress` запись о завершении (действие `"finish_lesson"`, время) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,time.time%28%29%20%7D%29%20self._save_progress)) и сохраняет прогресс. Затем выводит заключительное сообщение: “Урок завершён. Все части урока пройдены.” ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,1)). После этого формируется простая статистика: число пройденных частей из общего количества и время, затраченное на урок (разница между текущим временем и меткой времени первой записи прогресса, в минутах) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,total_parts%20%3D%20len%28self.lesson.parts)). Эта статистика выводится как Markdown список ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=stats%20%3D%20f,1)). *(Замечание: Если `lesson_progress` пуст или первая запись отсутствует, код может вызвать ошибку; предполагается, что к завершению урока прогресс не пуст.)*
  
  - `_save_progress()` – сохраняет текущий список `lesson_progress` в JSON-файл `lesson_file` (по умолчанию `"lesson.json"`). Реализовано через стандартный `json.dump` с `ensure_ascii=False` (чтобы сохранить Unicode символы как есть) и отступом для читабельности ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,lesson_progress%2C%20f%2C%20ensure_ascii%3DFalse%2C%20indent%3D2)). В случае ошибки при записи выводится сообщение об ошибке через `print` в консоль (например, недостаточно прав доступа и пр.) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=except%20Exception%20as%20e%3A%20print%28f,str%28e)).

В совокупности, `LearnlyEngine` управляет как статическим сценарием урока (части, определённые в `begin_lesson`), так и динамически генерируемыми заданиями через `show_task`. Однако, как будет отмечено далее, интеграция между этими двумя режимами пока не полная.

## Модуль `display.py` (отображение контента)

Этот модуль отвечает за вывод информации в ноутбуке в удобочитаемом формате. Класс **LearnlyDisplay** предоставляет методы, обёрнутые вокруг `IPython.display.display` и Markdown-разметки для форматирования текста.

Методы класса LearnlyDisplay:
- `show_welcome_message()` – выводит приветствие в начале урока. Форматируется крупным заголовком и нумерованным списком с инструкцией, как работать с ноутбуком (написать решение, запустить ячейку и получить обратную связь) ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=def%20show_welcome_message%28self%29%20,)). (В коде присутствует закомментированный блок с подсказкой о команде `hint` – видимо, планировалось дополнить инструкцию сообщением, что для запроса подсказки можно ввести `hint` в ячейке решения ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=,check_solution%22%20%23))).
- `show_text_content(content, part_index)` – выводит теоретический материал. Оформляется как заголовок третьего уровня с номером части и надписью "Часть", затем сам текст контента ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=def%20show_text_content,%7Bpart_index%20%2B%201%7D.%20%D0%A7%D0%B0%D1%81%D1%82%D1%8C%5Cn%7Bcontent)). Например: “### 1. Часть\n*текст урока*”.
- `show_assignment(content, part_index)` – выводит условие задания, оформляя аналогично, только с надписью "Задание" ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=def%20show_assignment,%7Bpart_index%20%2B%201%7D.%20%D0%97%D0%B0%D0%B4%D0%B0%D0%BD%D0%B8%D0%B5%5Cn%7Bcontent)) (например: “### 2. Задание\n*текст условия*”).
- `show_hint(hint)` – выводит подсказку с значком лампочки и полужирным шрифтом ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=def%20show_hint%28self%2C%20hint%3A%20str%29%20,%F0%9F%92%A1%20%2A%2A%D0%9F%D0%BE%D0%B4%D1%81%D0%BA%D0%B0%D0%B7%D0%BA%D0%B0%3A%2A%2A%20%7Bhint)), например: “💡 **Подсказка:** *текст подсказки*”.
- `show_example(example)` – выводит пример кода с значком заметки и оформляет его внутри блока кода Pytho ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=def%20show_example%28self%2C%20example%3A%20str%29%20,%F0%9F%93%9D%20%2A%2A%D0%9F%D1%80%D0%B8%D0%BC%D0%B5%D1%80%20%D0%BA%D0%BE%D0%B4%D0%B0%3A%2A%2A%5Cn%60%60%60python%5Cn%7Bexample%7D%5Cn))】. Если пример кода многострочный, он будет показан внутри markdown-блока ```python ... ```.
- `show_success(message)` – выводит сообщение об успешном выполнении с зелёным чекбокс-Emoj ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=def%20show_success%28self%2C%20message%3A%20str%29%20,%E2%9C%85%20%7Bmessage))】, например: “✅ Отлично! Задание выполнено правильно.”.
- `show_error(message)` – выводит сообщение об ошибке с красным крестико ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=def%20show_error%28self%2C%20message%3A%20str%29%20,%E2%9D%8C%20%7Bmessage))】, например: “❌ В вашем решении есть ошибка.”.
- `show_lesson_progress(progress_list)` – отображает ранее сохранённый прогресс урока. На вход подаётся список словарей `progress` (такой же, который сохраняется в JSON). Для каждой записи заново выводится либо часть урока, либо задание:
  - Если запись имеет `"type": "text"`, выводится заголовок "Часть {номер}" и контен ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=def%20show_lesson_progress%28self%2C%20progress%3A%20List,assignment))】.
  - Если `"type": "assignment"`, выводится "Задание {номер}" и условие задани ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=if%20entry.get%28%22type%22%29%20%3D%3D%20%22text%22%3A%20display%28Markdown%28f%22,%D0%9E%D1%82%D0%B2%D0%B5%D1%82%20%D1%83%D1%87%D0%B5%D0%BD%D0%B8%D0%BA%D0%B0%3A%2A%2A%5Cn%60%60%60python%5Cn%7Bentry%5B%27student_answer%27%5D%7D%5Cn))】. Также, если в записи присутствует ключ `"student_answer"`, дополнительно показывается ответ ученика, оформленный как блок код ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=display%28Markdown%28f%22,%D0%9E%D1%82%D0%B2%D0%B5%D1%82%20%D1%83%D1%87%D0%B5%D0%BD%D0%B8%D0%BA%D0%B0%3A%2A%2A%5Cn%60%60%60python%5Cn%7Bentry%5B%27student_answer%27%5D%7D%5Cn))】. Эта функция позволяет восстановить диалог урока, когда ученик возвращается: он увидит, какие части прошёл и что отвечал на задания.
  - Если тип не текст и не задание (например, `"code"`), такая запись не отображается – в текущем коде это ветвление не обрабатывает тип `"code"` вовсе (ещё один недочёт, см. ошибки).
- `show_lesson_summary(completed_tasks, topics)` – выводит краткое резюме урока: поздравление, сколько заданий выполнено, и перечисляет изученные тем ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=def%20show_lesson_summary,))】. В текущем коде `LearnlyEngine.finish_lesson()` не использует этот метод, вместо этого генерирует свою статистику; возможно, `show_lesson_summary` заложен на будущее, для более содержательного отчёта (например, перечисление тем урока).

В целом, `LearnlyDisplay` служит для отделения логики отображения от логики управления. Он делает выводы более красочными и понятными за счёт Markdown. При развитии проекта здесь можно улучшать интерфейс без изменения основного движка.

## Модуль `lesson.py` (генерация урока с помощью OpenAI)

Модуль `lesson.py` предназначен для интеграции с API OpenAI и автоматической генерации содержания урока или заданий. Здесь находятся:
- **`create_new_lesson()`** – функция, возвращающая структуру нового урока (в словарном виде). Сейчас она возвращает фиксированный словарь с тремя частями урок ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=def%20create_new_lesson%28%29%3A%20return%20%7B%20,print%28%27Hello%2C%20world))】: приветствие (text), пример кода `print('Hello, world!')` (code) и пояснение к этому коду (text). Эта функция используется в конструкторе LearnlyEngine для начальной инициализации `self.lesson`. Возможно, это была ранняя версия задания урока через словарь. После внедрения классов Lesson/Part её значение уменьшилось, хотя можно было бы использовать для быстрого старта или тестов. Она показывает пример структуры урока, где каждая часть описывается словарём с типом и контентом.
  
- **`generate_lesson_part(lesson) -> dict`** – функция для генерации следующей части урока на основе уже пройденного. Она формирует текстовый *prompt* (промпт) для модели GPT, описывая требования:
  1. Новый кусок урока должен быть связан с предыдущими и основываться на уже данных знаниях.
  2. Не повторять уже пройденный материа ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=prompt%20%3D%20%28%20,n%5Cn%D0%A3%D1%80%D0%BE%D0%BA%20%D0%BD%D0%B0%20%D0%B4%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9%20%D0%BC%D0%BE%D0%BC%D0%B5%D0%BD%D1%82%3A%5Cn%7Blesson%7D%5Cn%5Cn))】.
  
  В prompt также передаётся текущее состояние урока: `f"Урок на данный момент:\n{lesson}\n\n" ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=,n))】. Переменная `lesson` здесь, вероятно, предполагается быть текстовым представлением урока (например, перечислением уже имеющихся частей и их содержания).
  
  Далее промпт инструктирует сгенерировать фрагмент урока в формате JSON, например:
  ```json
  {
      'type': 'text',
      'content': [текст новой части]
  }
  ``` 
  и просит вывести **только JSON** без Markdown-разметк ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=prompt%20%2B%3D%20%28%20,))】. Обратите внимание: ключи и строки в примере указаны в одинарных кавычках – формально это невалидный JSON, но валидный Python-словарь. Вероятно, это сделано намеренно.
  
  Затем выполняется вызов `openai.ChatCompletion.create(...)` с моделью (в коде указано `"gpt-4o"`, что может быть кастомным именем модели, например GPT-4), передаются роли "system" и "user" с соответствующим контексто ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=%23%20TODO%3A%20openai%200.28.%2A%20,prompt%7D%20%5D%2C%20max_tokens%3D500))】. Параметры: `max_tokens=500` и `temperature=0.7` (креативность модели). Предполагается, что OpenAI вернёт продолжение в формате указанного словаря.
  
  Результат от API извлекается как строка `generated_text` – содержимое первого ответа модел ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=generated_text%20%3D%20response))】. **Важно:** Далее код пытается **распарсить сгенерированный текст через `eval()`* ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=,return%20None))】. То есть, если модель вернёт строку вида `"{ 'type': 'text', 'content': 'Новый материал' }"`, функция `eval` преобразует её в Python-словарь `new_lesson_part`. Если парсинг прошёл успешно, этот словарь возвращается. Если произошла ошибка (например, модель вернула невалидный код), она будет выведена в консоль, а функция вернёт Non ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=new_lesson_part%20%3D%20eval,return%20None))】.
  
  Использование `eval` на тексте, полученном от модели, – решение спорное и небезопасное. Ниже в разделе "Ошибки и уязвимости" мы рассмотрим риски этого подхода.
  
- **Прочие элементы модуля:** В начале файла импортируется `openai` и типы. Также присутствует большой комментарий с примерами заданий в формате словаря (несколько примеров задач с `problem`, `hint`, `check`, `error`, `success` ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=%D0%95%D1%89%D0%B5%20%D0%BF%D1%80%D0%B8%D0%BC%D0%B5%D1%80%D1%8B%20%D0%B7%D0%B0%D0%B4%D0%B0%D0%BD%D0%B8%D0%B9%3A%20self,%D0%9E%D1%82%D0%BB%D0%B8%D1%87%D0%BD%D0%BE%21%20%D0%97%D0%B0%D0%B4%D0%B0%D0%BD%D0%B8%D0%B5%20%D0%B2%D1%8B%D0%BF%D0%BE%D0%BB%D0%BD%D0%B5%D0%BD%D0%BE%20%D0%BF%D1%80%D0%B0%D0%B2%D0%B8%D0%BB%D1%8C%D0%BD%D0%BE%21%27)) ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=2%3A%20,%D0%92%D1%8B%20%D1%81%D0%BF%D1%80%D0%B0%D0%B2%D0%B8%D0%BB%D0%B8%D1%81%D1%8C%20%D1%81%D0%BE%20%D0%B2%D1%82%D0%BE%D1%80%D1%8B%D0%BC%20%D0%B7%D0%B0%D0%B4%D0%B0%D0%BD%D0%B8%D0%B5%D0%BC)) ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=3%3A%20,%D0%9F%D1%80%D0%BE%D0%B2%D0%B5%D1%80%D1%8C%D1%82%D0%B5))】. Этот комментарий демонстрирует, как может выглядеть база заданий или формат генерации задач. Вероятно, это примеры, которые хотели использовать при разработке или для вдохновения при генерации через ИИ. 
  Есть также комментарий о запросе к AI: "Обращаемся к AI и просим его написать задание... ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=%D0%9E%D0%B1%D1%80%D0%B0%D1%89%D0%B0%D0%B5%D0%BC%D1%81%D1%8F%20%D0%BA%20AI%20%D0%B8%20%D0%BF%D1%80%D0%BE%D1%81%D0%B8%D0%BC,%D0%9E%D1%82%D0%BB%D0%B8%D1%87%D0%BD%D0%BE%21%20%D0%97%D0%B0%D0%B4%D0%B0%D0%BD%D0%B8%D0%B5%20%D0%B2%D1%8B%D0%BF%D0%BE%D0%BB%D0%BD%D0%B5%D0%BD%D0%BE%20%D0%BF%D1%80%D0%B0%D0%B2%D0%B8%D0%BB%D1%8C%D0%BD%D0%BE%21%27))】, но явной функции, генерирующей задания (с полями `check`, `success` и т.д.), в коде пока нет. Возможно, планируется объединить логику из этих примеров с функцией `generate_lesson_part` или создать отдельную функцию для генерации практических задач (AssignmentPart) с автоматической проверкой.

В ноутбуке можно видеть соответствующие отображения: приветственное сообщение (заголовок "Добро пожаловать в Learnly! ..." и инструкция) и затем первую часть урока ("1. Часть ..." ([learnly.ipynb](file://file-SNuogo3itRxA51JiqJQ3QD#:~:text=%22data%22%3A%20%7B%20%22text%2Fmarkdown%22%3A%20%5B%20%22,)) ([learnly.ipynb](file://file-SNuogo3itRxA51JiqJQ3QD#:~:text=%7B%20,IPython.core.display.Markdown%20object))】.

- При нажатии "Дальше" выводится второе задание ("2. - Далее, вероятно, пользователь должен либо ввести решение в предоставленное поле и нажать "Дальше", либо воспользоваться сгенерированной ячейкой `%%check_solution` (если она была создана) для проверки. В примере notebook видно, что после задания сразу показывается текстовое поле (Textarea ([learnly.ipynb](file://file-SNuogo3itRxA51JiqJQ3QD#:~:text=%7B%20%22data%22%3A%20%7B%20%22application%2Fvnd.jupyter.widget,value%3D%27%27%2C%20description%3D%27%D0%92%D0%B0%D1%88%20%D0%BE%D1%82%D0%B2%D0%B5%D1%82%3A%27%2C%20placeholder%3D%27%D0%92%D0%B2%D0%B5%D0%B4%D0%B8%D1%82%D0%B5%20%D0%B2%D0%B0%D1%88))】, но нет явного вывода результата проверки. Таким образом, `learnly.ipynb` служит для запуска движка и наблюдения за работой UI. Особого функционального кода (кроме вызова методов `LearnlyEngine`) в нём нет, но он подтверждает, что основной сценарий – запуск в Jupyter с использованием виджетов и Markdown вывода.

# Найденные проблемы и потенциальные уязвимости

При анализе кода выявлен ряд ошибок, недочётов и проблем безопасности:

**1. Неполная десериализация урока (потеря данных при загрузке):** В методе `Lesson.from_dict` не обрабатывается тип части `"code" ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=for%20part_data%20in%20data.get%28,add_part%28part))】. Если урок, сохранённый в JSON, содержит части с типом "code", при загрузке они будут проигнорированы (ветка `else: continue`). Это явная ошибка: например, урок, созданный `create_new_lesson()` с частями text-code-text при восстановлении потеряет среднюю часть кода. Также, AssignmentPart восстанавливается не полностью – специальные поля `success_message` и `error_message` не читаются из словаря. Поскольку `AssignmentPart.from_dict` не переопределён, будет вызван базовый LessonPart.from_dict, который игнорирует эти поля. В итоге при загрузке прогресса кастомные сообщения успеха/ошибки для задания собьются на значения по умолчанию. Такая неполная десериализация делает сохранение/загрузку урока ненадёжной.

**2. Отсутствие реализации проверки решения для встроенных заданий урока:** В сценарии `LearnlyEngine.begin_lesson` одно из частей – задание (AssignmentPart). Однако нигде не прописано, как проверять решение именно для этой части. В `LearnlyEngine.check_solution` проверка основана на поиске задания в `self.memory['tasks']` по индекс ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=task_index%20%3D%20self,success%27%5D%29%20time.sleep%281%29%20self.advance_to_next_task%28%29%20else))】. Но при отображении встроенного задания через `_display_current_part`, в `memory['tasks']` ничего не добавляется (в отличие от динамических задач через `show_task`). Поэтому, если ученик попытается проверить решение задания №2 (например, написать функцию суммы) и запустить `%%check_solution`, метод `check_solution` не найдёт соответствующего `task` и просто ничего не сделает. По сути, для заданий, определённых внутри урока (AssignmentPart из списка parts), автоматическая проверка не реализована. Вероятно, планировалось либо генерировать все задания через `show_task`/`memory['tasks']`, либо задать для AssignmentPart свой механизм проверки. Этот пробел – логическая ошибка: ученик может выполнить задание, но система не даст ни подтверждения правильности, ни указания на ошибку (если не считать возможность нажать "Дальше" и просто увидеть следующий текст, минуя проверку).

**3. Нереализованная магическая команда `%%check_solution`:** Код подразумевает использование кастомной cell magic `%%check_solution` для проверки решений (через `set_next_input` новая ячейка помечается этой командой ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=def%20create_solution_cell%28self%2C%20problem%3A%20str%29%20,replace%3DFalse))】. Однако в коде нет регистрации такой магии. IPython позволяет определить функции для обработки `%%` команд с помощью `register_cell_magic`, но в `engine.py` зарегистрирована только строковая магия `%reload_learnly` для перезагрузки модул ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=ipython%20%3D%20get_ipython,magic%20import%20register_line_magic%2C%20register_cell_magic)) ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=,register_magic_function%28reload_learnly%2C%20%27line))】. Команды `%%check_solution` не существует, и если выполнить такую ячейку, возникнет ошибка `UnknownCellMagic`. Судя по всему, функциональность проверки задумывалась либо через магию, либо через обработку виджета. Отсутствие реализации – явный баг. Без этого автоматическая проверка решений (п.2) не будет работать вообще, даже для динамических задач, потому что запуск ячейки `%%check_solution` не вызовет `LearnlyEngine.check_solution`. 

**4. Некорректная обработка ввода пользователя (поиск команд в тексте решения):** Метод `check_solution` анализирует текст пользовательской ячейки на содержание слов `'hint'`, `'help'`, `'skip'`, `'finish'` простым вхождением подстрок ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=clean_cell%20%3D%20cell))】. Это означает, что если решение ученика *случайно* содержит эти последовательности букв, сработает соответствующее действие. Например, переменная или функция с именем `finish_task` или просто комментарий "skip this part" приведут к нежелательному завершению урока или пропуску задания. Корректнее было бы проверять команду более строго (например, весь текст ячейки равен определённому слову, либо начинается с него). Также, команда `help` может встречаться как функция `help()` или строка, и её появление в любом месте кода вызовет подсказку. Такой подход может привести к путанице и ложным срабатываниям. Это скорее недоработка UX-логики.

**5. Использование опасной функции `eval` на тексте от внешней модели:** В `lesson.py` для парсинга ответа модели используется `eval() ([lesson.py](file://file-4SbaabcQt9eygnoXjp2rXZ#:~:text=,return%20None))】. Это представляет **серьёзную уязвимость безопасности**. Если модель OpenAI (особенно GPT-4 с высокой креативностью) вернёт текст, содержащий произвольный код (например, вызов системной команды, обращение к файловой системе), `eval` его выполнит. Хотя prompt просит формат JSON, модель может ошибиться или злоумышленник теоретически может повлиять на вывод. Использование `eval` на непроверенных данных открывает возможность выполнения произвольного кода, что недопустимо. Нужно применять безопасный парсер, например `json.loads()` или хотя бы `ast.literal_eval` (который не выполняет выражения, а только парсит литералы). Кроме того, `eval` здесь полагается, что вывод – валидный Python-словарь. Если модель вернёт JSON с двойными кавычками, `eval` упадёт с ошибкой. Этот фрагмент требует переработки и является уязвимым местом.

**6. Проблемы с сохранением и восстановлением прогресса:**
  - В конструкторе LearnlyEngine сразу сбрасывается файл прогресса (`_save_progress()` вызывается на пустом списке ([engine.py](file://file-3NDfRMP6rvtXjbcY4MSr8a#:~:text=self.memory%3A%20Dict%5Bstr%2C%20Any%5D%20%3D%20,))】, что может стереть предыдущий прогресс до попытки его загрузить. Например, если урок прерывался и файл `lesson.json` остался, при создании нового LearnlyEngine файл тут же перезаписывается пустым, и `start_lesson` уже ничего не загрузит. Это логическая ошибка: надо либо сохранять прогресс *после* загрузки (что противоречит цели), либо не перезаписывать, если файл уже существует и мы хотим восстановиться. Сейчас же фактически резюме урока не сохраняется между запусками, несмотря на наличие механизма.
  - В `display.show_lesson_progress` не обрабатываются записи типа `"code" ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=if%20entry.get%28%22type%22%29%20%3D%3D%20%22text%22%3A%20display%28Markdown%28f%22,%D0%9E%D1%82%D0%B2%D0%B5%D1%82%20%D1%83%D1%87%D0%B5%D0%BD%D0%B8%D0%BA%D0%B0%3A%2A%2A%5Cn%60%60%60python%5Cn%7Bentry%5B%27student_answer%27%5D%7D%5Cn))】, хотя прогресс может включать такие (если бы сохранялись CodePart). Записи с кодом просто пропадут из отображения истории.
  - Предусмотрено поле `"student_answer"` в записях прогресса (для заданий, ответ ученика ([display.py](file://file-1LKn9GWCYQYmcLN5ncnHB7#:~:text=display%28Markdown%28f%22,%D0%9E%D1%82%D0%B2%D0%B5%D1%82%20%D1%83%D1%87%D0%B5%D0%BD%D0%B8%D0%BA%D0%B0%3A%2A%2A%5Cn%60%60%60python%5Cn%7Bentry%5B%27student_answer%27%5D%7D%5Cn))】, но нигде в коде оно не присваивается. Например, логично было бы при неудачной попытке или успешной проверке сохранять решение пользователя. Этого нет, так что данный функционал не завершён.
  
**7. Логика UI для заданий не завершена:** В текущем виде, когда выводится AssignmentPart через `_display_current_part`, показывается текст задания и поле ввода, но **нет способа отправить введённый код на проверку**. Пользователь может нажать кнопку "Дальше", но это просто перейдёт к следующей части, не зная, правильный ли ответ (система не проверяет содержимое Textarea). Предположительно, задумка была, что пользователь либо выполнит созданную ячейку `%%check_solution` (которая должна появиться, если задание было динамическим через `show_task`), либо поле ввода должно как-то связаться с кодом. Однако ни обработчика нажатия "Дальше" для захвата содержимого Textarea, ни кнопки "Проверить" нет. В результате задание внутри урока можно фактически пропустить, просто нажав "Дальше". Это нарушение логики обучения. Вероятно, разработчики планировали другой подход (например, все задания проводить через `show_task`, а не через встроенный AssignmentPart), или добавить обработку содержимого виджета. В текущем состоянии, UI заданий не доведён до конца.

**8. Мелкие проблемы:**
  - Выбор модели `"gpt-4o"` в OpenAI API – нестандартное имя (возможно опечатка или внутреннее обозначение). Это вызовет ошибку, если API не распознает модель. Вероятно, имелся в виду `gpt-4` или другая доступная модель.
  - Отсутствует обработка ошибок вызова OpenAI API (если нет подключения или неверный ключ). Код `ChatCompletion.create` не обёрнут в try/except, и ошибка приведёт к падению функции `generate_lesson_part`. Только ошибки при `eval` перехватываются, но если сама API вызовет исключение (например, `openai.error.OpenAIError`), его никак не обработают.
  - Имена на русском для действий в прогрессе (e.g., `"расскажи подробнее"`, `"пропуск_задания"`) – это не ошибка, но нужно учитывать, что смешивание языков и пробелы может затруднить обработку данных (например, при анализе логов или расширении функционала).
  - В README и коде заметны опечатки (`Улучить интерфейс` вместо `Улучшить ([README.md](file://file-JfqCXbnsBKUdsYMM1Bxu49#:~:text=TODO%3A%20%D0%B2%20%D0%B1%D1%83%D0%B4%D1%83%D1%89%D0%B5%D0%BC%20,))】, `выполненыые` вместо `выполненные ([README.md](file://file-JfqCXbnsBKUdsYMM1Bxu49#:~:text=,%D0%BE%D0%B1%20%D1%83%D1%87%D0%B5%D0%BD%D0%B8%D0%BA%D0%B5%3A%20%D1%83%D1%80%D0%BE%D0%B2%D0%B5%D0%BD%D1%8C%2C%20%D1%81%D1%82%D0%B8%D0%BB%D1%8C%20%D0%BE%D0%B1%D1%89%D0%B5%D0%BD%D0%B8%D1%8F))】, и т.д.), но это косметические моменты.

В совокупности, самые серьёзные – п.2 (неработающая проверка встроенных заданий) и п.5 (уязвимость eval). Они требуют приоритетного внимания. 

# Предложения по исправлению ошибок и улучшению кода

**1. Полная сериализация/десериализация урока:** 
   - В методе `Lesson.from_dict` необходимо добавить обработку всех типов частей. Следует распознавать `"code"` и восстанавливать через `CodePart.from_dict`. Кроме того, стоит предусмотреть расширение на новые типы (например, если появятся другие LessonPart). Можно сделать через словарь соответствий типа и класса, либо через регистрационный механизм. Пример исправления:
     ```python
     part_type = part_data.get("type")
     if part_type == "text":
         part = TextPart.from_dict(part_data)
     elif part_type == "code":
         part = CodePart.from_dict(part_data)
     elif part_type == "assignment":
         part = AssignmentPart.from_dict(part_data)
     else:
         continue
     lesson.add_part(part)
     ```
     Так все части восстановятся корректно.
   - Для AssignmentPart стоит реализовать свой `from_dict`, который будет учитывать поля `success_message` и `error_message`. Либо, проще, после создания объекта через базовый from_dict дополнительно установить `instance.success_message = data.get("success_message", default)` и аналогично для error. Например:
     ```python
     @classmethod
     def from_dict(cls, data):
         instance = super().from_dict(data)  # вернет AssignmentPart с content, hint, example
         if isinstance(instance, AssignmentPart):
             instance.success_message = data.get("success_message", instance.success_message)
             instance.error_message = data.get("error_message", instance.error_message)
         return instance
     ```
     Тогда уникальные поля не потеряются.
   - При сохранении прогресса можно записывать в JSON не только списки действий, но и, например, сохранять текущий индекс или состояние memory (заданий). Но это уже расширение функционала по сохранению.

**2. Реализация проверки для заданий внутри урока:** 
   Есть несколько путей решить проблему отсутствия проверки:
   - **Вариант A:** При создании Lesson и добавлении AssignmentPart предусмотреть, как будет проверяться правильность. Можно расширить AssignmentPart, чтобы он содержал, например, функцию проверки или хотя бы ожидаемый результат. Например, AssignmentPart может принимать параметр `check_func` (callable), который знает, как проверить решение. В уроке при конструировании задания разработчик задаст эту функцию. В примере задания "функция суммы" check_func мог бы быть `lambda ns: 'add' in ns and callable(ns['add']) and ns['add'](2,3)==5`. Тогда в `check_solution` можно было бы, обнаружив, что текущая часть – AssignmentPart, вызывать не memory['tasks'] (пусто), а `self.lesson.parts[task_index].check_func(ns)`. Для реализации потребуются изменения: хранить check_func, сохранять его нельзя напрямую (но можно по имени или не сохранять вовсе – проверка нужна только в живой сессии).
   - **Вариант B:** Более простой – привязать AssignmentPart к механизму memory['tasks']. Например, при добавлении AssignmentPart в урок автоматически добавлять соответствующую задачу в `memory['tasks']` с тем же индексом. Нужно где-то описать логику проверки. Можно поступить так: когда создаётся AssignmentPart, разработчик указывает пример решения (`example`) и, возможно, ожидаемый результат. На базе этого генерировать функцию `check`. Например, для функции можно попытаться проверить, что определена функция с определённым именем или что выход совпадает с примером. Это требует дополнительного кода, но даст единообразие – все задания (статические и динамические) хранятся и проверяются через `memory['tasks']`. 
   - **Вариант C:** Упростить – сделать так, что AssignmentPart внутри урока не требует автоматической проверки, а служит как открытое задание для обсуждения. Однако это противоречит интерактивности. Лучше всё же реализовать проверку.
   
   Любой из подходов потребует доработать `check_solution` и `_display_current_part`. Например, если AssignmentPart будет проверяться через memory, тогда при отображении AssignmentPart стоит создавать ячейку `%%check_solution` так же, как делает `show_task`. Сейчас `_display_current_part` просто показывает Textarea, но лучше вместо/дополнительно **автоматически вызывать `create_solution_cell`** для AssignmentPart. Тогда поведение встроенного задания будет такое же, как динамического: под заданием сразу появится ячейка, где ученик пишет код и запускает её. Для этого, в `_display_current_part`:
   ```python
   if isinstance(current_part, AssignmentPart):
       self.create_solution_cell(current_part.content)
   ```
   вместо (или вместе с) вывода Textarea. Либо привязать кнопку "Дальше" для задания к выполнению проверки. Но использование единого механизма с магией `%%check_solution` более гармонично.
   
   Ну и главное – нужно реализовать саму магическую команду (следующий пункт).

**3. Реализовать магию `%%check_solution` или альтернативный способ проверки:**
   - **Способ 1: Магическая команда.** Добавить в `engine.py` регистрацию cell magic, аналогично `reload_learnly`. Например:
     ```python
     def check_solution_magic(line, cell):
         engine = ...  # как получить текущий LearnlyEngine?
         engine.check_solution(cell, globals())
     if ipython is not None:
         ipython.register_magic_function(check_solution_magic, 'cell', 'check_solution')
     ```
     Здесь есть вопрос с доступом к экземпляру LearnlyEngine. Возможно, его можно хранить в глобальной переменной или как Singleton. В Jupyter не лучшая практика, но рабочий вариант – при создании движка присвоить `global current_engine = engine` и внутри магии обращаться к ней. Или регистрировать магию прямо из метода объекта (менее удобно). Тем не менее, реализация магической команды позволит, запуская ячейку с `%%check_solution`, автоматически вызывать `engine.check_solution` на код ячейки.
   - **Способ 2: Отказ от магии, использование виджетов.** Можно вовсе убрать добавление `%%check_solution` и Textarea. Вместо этого при выводе задания размещать Textarea для ввода кода *и кнопку* "Проверить". Кнопке привязать обработчик: он берет содержимое Textarea, выполняет его (через `exec` в отдельном namespace) и применяет проверку. Это сложнее реализовать, но избавляет от необходимости магии и более привычно для пользователя (не нужно вручную запускать новую ячейку, достаточно нажать кнопку проверки). Однако, выполнение произвольного кода через exec в виджете тоже требует предусмотреть безопасность.
   - Возможно, стоит оставить оба варианта: магия для тех, кому удобнее работать в клетках, и виджет-кнопка для интерфейсного стиля.
   - В контексте нынешнего кода, быстрее всего внедрить cell magic. Это исправит баг №3 и обеспечит вызов проверки (при наличии исправлений из п.2). 

**4. Улучшение распознавания команд в тексте решения:**
   - Чтобы избежать ложных срабатываний, проверку команд (`hint`, `skip`, etc.) лучше делать по конкретным словам. Например, разбить `clean_cell` по пробельным символам и сравнивать первые слова или использовать регулярные выражения (`^hint$` и т.д.). Ещё вариант – требовать, чтобы команда была единственным словом в ячейке. Тогда ученик, чтобы пропустить, должен ввести именно `skip`. 
   - Как улучшение UX, можно явно перечислять пользователю, какие команды доступны (например, добавить это в приветственное сообщение или при выводе задания: "*Вы можете ввести 'hint' для подсказки, 'skip' чтобы пропустить.*").
   - Также стоит обработать обе раскладки (английские слова или их русские аналоги?). Сейчас используются англ. слова, что не совсем соответствует остальному русскоязычному интерфейсу. Возможно, имеет смысл заменить их на `подсказка`, `пропустить` и т.д., чтобы пользователь вводил команды на русском, или хотя бы документировать, что команды на англ. 
   - Сами действия (показ подсказки, пропуск) реализованы, нужно только надёжнее их вызывать.

**5. Безопасное парсинг вывода OpenAI:**
   - **Заменить `eval` на безопасный парсер.** Если модель возвращает JSON-строку, лучше использовать `json.loads(generated_text)`. Для этого, правда, нужно убедиться, что текст действительно валидный JSON. В prompt можно настоять на двойных кавычках и валидном JSON. Если хочется поддержать Python-словарный формат, то хотя бы `ast.literal_eval(generated_text)` – он не выполнит вызовы функций или выражений, а только литералы (словарь, строки, числа). Это существенно снизит риск по сравнению с `eval`. 
   - Добавить проверку/очистку строки перед парсингом. Например, убрать опасные подстроки, или проверить, что начало – “{” и конец – “}”. Хотя это слабая защита, но уже что-то.
   - В идеале, вообще не полагаться на исполнение кода из модели. Лучше написать парсер, ожидающий конкретную структуру. Например, можно попросить модель возвращать не Python-словарь, а JSON, и потом сделать `json.loads`. Если нужно поддержать лямбда-функции или код (например, проверка `check`), то лучше генерировать код отдельно и не исполнять его автоматически без проверки.
   - В дополнение – ограничить функциональность eval. Но так как цель просто получить словарь, лишнее.
   - Также, обработать случаи, когда модель вернула не то, что ожидалось: сейчас код печатает ошибку и сам текст. Возможно, лучше пробросить исключение выше или вернуть специальный результат. Как вариант: возвращать пустой словарь или с полем `"type": "text", "content": "Извините, произошла ошибка генерации..."` – чтобы урок мог продолжиться даже если ИИ не ответил.

**6. Исправить логику сохранения/загрузки прогресса:**
   - Не очищать файл прогресса при каждом запуске. Решение: убрать вызов `_save_progress` из конструктора `__init__`. Прогресс должен либо загружаться, либо создаваться новый, но не затираться до загрузки. Можно сделать так:
     ```python
     self.lesson_progress = []
     if os.path.exists(self.lesson_file):
         # либо сразу загрузить сюда, либо отложить до start_lesson
         # Возможно, лучше не грузить в __init__, а только в start_lesson, 
         # но и не стирать файл до этого.
         pass
     ```
     Сохранение в файл можно производить только при изменении прогресса, что и делается дальше в коде. Если же нужен сброс прогресса для нового урока, можно предоставить пользователю выбор (например, отдельный метод "new_lesson" или удаление файла).
   - При отображении прогресса (`show_lesson_progress`) добавить поддержку кода. Например, можно обрабатывать тип `"code"` аналогично `"text"`, т.к. по сути это теоретический материал, просто написанный как код. Показывать его можно в формате кода: 
     ```python
     elif entry.get("type") == "code":
         display(Markdown(f"### {entry['part_index'] + 1}. Пример кода\n```python\n{entry['content']}\n```"))
     ```
     Это позволит видеть пройденные примеры кода при восстановлении урока.
   - Запись ответа ученика. Можно в `check_solution` при неправильном решении или даже при любом выполнении добавлять в `lesson_progress` поле `"student_answer": код_решения` (возможно, усечённый или очищенный). Тогда при возобновлении урока в `show_lesson_progress` появится этот код под условием задания, что поможет вспомнить, что ученик пытался сделать. Например, при каждом запуске `check_solution`, перед проверкой, добавлять временно что-то вроде:
     ```python
     self.lesson_progress.append({
         "part_index": task_index,
         "type": "assignment",
         "content": task['problem'],
         "student_answer": cell,
         "timestamp": time.time()
     })
     ```
     Но тут нужно аккуратно: прогресс сильно разрастётся, т.к. каждое повторное выполнение будет новой записью. Возможно, логичнее обновлять последнюю запись задания, добавляя туда student_answer, а не добавлять новую. Детали зависят от того, как хотим хранить историю.
   
**7. Доработка UI для ввода и проверки решений:**
   - Как было отмечено, есть два подхода: cell magic или виджеты. Если идём по пути cell magic, то при показе задания (как в `show_task`) уже всё работает через новую ячейку. Нужно только сделать то же для заданий из урока (AssignmentPart).
   - Если хотим задействовать `widgets.Textarea` для ввода ответа, следует добавить кнопку "Проверить" рядом. Можно, например, модифицировать `_create_command_widget` для заданий: если текущий `part` – AssignmentPart, добавить в HBox ещё одну кнопку "Проверить решение". При её нажатии выполнять код из Textarea. 
     - Выполнение можно реализовать, используя `exec`: создать новый словарь `ns = {}`, выполнить `exec(answer_code, ns)` и затем применить ту же `check` логику. Но `exec` так же опасен, как и выполнение через магию (ведь ученик может написать любой код, вплоть до `os.remove(...)`). Впрочем, так или иначе, мы выполняем код пользователя – sandboxing отсутствует. Это уже вопрос доверия/ограничений Jupyter (в Jupyter ученику и так доступен питон-ядро, они могут запустить любой код).
     - После выполнения и проверки можно отображать `show_success`/`show_error` аналогично.
     - Этот путь более сложен, поэтому магия – проще, но виджеты сделали бы UI целостным (всё через кнопки).
   - Обязательно синхронизировать эти два способа, чтобы не дублировать функциональность.
   - Улучшить доступность подсказок: сейчас подсказка и пример – по кнопкам. Это хорошо. Можно также при повторном неправильном ответе автоматически предлагать подсказку или сокращать количество попыток – но это уже методика обучения, за рамками технического улучшения.

**8. Другие улучшения и рефакторинг:**
   - Разделить генерацию урока и проведение урока. Например, `lesson.py` с openAI можно отделить от `LearnlyEngine`. Сделать класс, который отвечает за создание контента с ИИ (LessonGenerator), который мог бы генерировать новые части урока по запросу. Тогда `LearnlyEngine` мог бы вызывать его при необходимости (например, когда закончились заранее заготовленные части или по нажатию специальной кнопки "Продолжить урок").
   - Обработка исключений OpenAI: окружить вызов API try/except, выводить понятное сообщение (вдруг нет интернета или ключ неверен), чтобы программа не упала.
   - Локализация команд: решить, используются ли английские команды (hint, skip) или перейти на русский полностью, для консистентности.
   - Логгирование: заменить `print` на логгер или на вывод через `display.show_error` (например, если не смогли сохранить файл прогресса, вывести это в интерфейс, а не только в консоль, чтобы пользователь знал).
   - Убрать magic numbers: например, ширина строки 77 в `_wrap_text` – вынести в константу, чтобы было очевидно, что это за число (вероятно связано с шириной окна).
   - Понятность кода: добавить комментарии и docstring там, где их нет, особенно к публичным методам. Часть функций имеет докстринги (на русском, что хорошо), но можно покрыть всё для единого стиля.
   - Исправить опечатки и оформить README. README сейчас содержит скорее план, чем описание. Можно дополнить его итоговой информацией о запуске и использовании.

# Рекомендации по оптимизации проекта

С точки зрения **производительности**, текущий проект не содержит тяжёлых вычислений, поэтому оптимизации скорее касаются опыта использования и масштабируемости:

- **Оптимизация работы с OpenAI:** В случаях генерации новых частей урока может быть полезно кешировать результаты или формировать минимальные запросы. Например, вместо пересылки всего урока в prompt (что может быть объёмно), можно отправлять только краткую сводку пройденного или последние несколько шагов. Это снизит токен-затраты и время отклика. Также, если уроки генерируются часто, стоит предусмотреть асинхронный вызов, чтобы UI не зависал, но в Jupyter это сложнее.
- **Масштабирование структуры урока:** Если планируется много частей, стоит убедиться, что хранение прогресса в списке и его частая запись не станет узким местом. Сейчас каждая часть сразу сохраняется в JSON. Для небольших уроков это нормально, но если представить урок из, скажем, 100 шагов, перезаписывать файл 100 раз – не критично, но можно группировать сохранения (например, сохранять раз в N шагов или по завершении). Однако надежность данных важнее, так что текущее решение приемлемо.
- **Оптимизация UI в ноутбуке:** Когда частей становится много, большое количество Markdown-выводов может затруднить навигацию (но с другой стороны, так сохраняется весь контент). Можно предусмотреть сворачивание пройденных частей или очистку вывода перед выводом новой (но тогда история пропадёт). Здесь баланс между наглядностью и удобством: может, лучше выводить весь диалог, но можно и очищать после окончания урока.
- **Использование памяти:** Объект `LearnlyEngine` хранит `lesson` и `lesson_progress` дублирующе (по сути, `lesson.parts` и `lesson_progress` обе хранят информацию о пройденных частях). Можно подумать, нужно ли хранить оба. `lesson_progress` скорее для сохранения и отображения истории, а `lesson` – исходная структура. Это нормально. Если добавить "память AI" как в README, надо продумать формат и объем данных (например, хранить частые ошибки, чтобы подсказки улучшать). Возможно, использовать базу данных или файлы.
- **Загрузка/выгрузка уроков:** Если предполагается много уроков или длительный курс, можно оптимизировать хранение: разделить прогресс по урокам (например, разные файлы для каждого урока), сохранять доп. информацию (время, оценки и т.п.). Пока проект небольшой, JSON-файл достаточен.
- **Обновление интерфейса:** Ipywidgets достаточно эффективны для нескольких кнопок, но если масштабировать интерфейс (например, десятки элементов), стоит следить за производительностью. В нашем случае максимум 5 кнопок – не проблема.
- **Совместимость:** Обратить внимание на версию OpenAI – обновление до 1.x могло бы дать преимущества (например, более стабильный API). Использование `python-dotenv` подразумевает загрузку `.env` для API ключа – нужно убедиться, что это делается (например, добавить `load_dotenv()` при инициализации, иначе пакет не используется).
- **Оптимизация кода и поддержки:** Структурировать проект в пакет. Сейчас модули лежат вместе; можно оформить их как пакет `learnly`, чтобы устанавливать через pip и проще импортировать (`from learnly.engine import LearnlyEngine`, и т.д.). Это организационная оптимизация, облегчающая повторное использование.
- **Визуализация и дополнительные возможности:** В README упомянуты планы по графикам (matplotlib, Plotly). Их внедрение может повлиять на производительность (построение графиков – тяжелее, чем вывод Markdown). Нужно будет оптимизировать, возможно, предварительно вычислять данные для графиков.
- **AI Model optimization:** Если генерация уроков на лету будет частой, можно подумать о fine-tuning модели или использовании локальных моделей для снижения затрат. Хотя это выходит за рамки конкретно оптимизации кода, но важно для практического проекта.

В целом, для текущего состояния проекта важнее исправить корректность и безопасность, а оптимизация по скорости не критична. Тем не менее, заложенные архитектурные решения (разделение на модули, использование виджетов) вполне масштабируемы для усложнения функционала.
